## 本次更新（9.9.1 → 9.9.2）

> **纯热修版本**：无新增功能、**无数据库结构变更**，覆盖解压即生效。
> 本版修掉的三处断链均系 9.8.3 内核自带（非社区版引入），其中最严重的一处让「提Bug」整条链路不可用。

### 问题修复

- **修复「提Bug」在全站 100% 报错的致命错误**（PHP 8 兼容）。`module/bug/control.php` 与
  `module/testcase/control.php` 用了 `parse_str($str)` 的**单参形式** —— 该写法靠自动注入
  当前作用域，PHP 8 已移除，一命中即 `ArgumentCountError`。表现为：产品页「提Bug」、
  测试执行里「用例结果提Bug」打开就是白屏/500，**管理员也无法新建 Bug**。
  两处均改为显式接出数组再 `extract`，行为与原先一致。

- **修复 CLI 升级通道静默失效**。README 写明的无 Web 暴露升级路径
  `php bin/ztcli 'http://<host>/upgrade-execute.html'` 实际**什么都没做**：CLI 下框架没有
  登录态、把用户置为 guest，而 guest 组没有任何 upgrade 权限，请求被权限守卫拒绝，
  `ztcli` 以退出码 0 结束且无任何输出 —— 照文档操作的人会以为升级成功。
  现已在 `isOpenMethod()` 中仅对 **CLI** 放行 `upgrade` 的 `execute`/`afterExec`
  两个方法；Web 路径不受影响（`upgrade.php` 仍由 web server 的 404 规则封禁）。

- **修复文档「全部文档库」页在异常 type 下 500**：`doc/alllibs` 视图对非
  `product`/`project` 的 type 直接 `count($subLibs[$lib->id])`，该键不存在时
  `count(null)` 在 PHP 8 抛 `TypeError`。已加存在性守卫。

### 是否建议升级

- **强烈建议**。第一项让「提Bug」完全不可用，任何在用 Bug 管理的站点都受影响。
- 升级方式：可直接覆盖解压（本版无数据库变更）；若站点规范要求走升级流程，用下方 CLI 通道即可
  —— 注意本版的 CLI 通道修复**只有在升级到 9.9.2 之后**才生效，若旧版 CLI 被拒，
  先用 Web 向导完成本次升级。
